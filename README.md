# PPM MVP — макет управления портфелем ИТ-проектов

Учебный проект для дисциплины «Верификация информационных систем». Реализует основной сквозной сценарий из ЛР №3–6: подача заявки → назначение экспертов → расчёт рейтинга → моделирование бюджета → голосование инвестиционного комитета → CSV-экспорт и аудит.

> **Важное ограничение:** это учебный MVP, а не production-система. В Compose включены демонстрационные пароли, самоподписанный TLS-сертификат и каталог LDAP с паролями из LDIF. Не открывайте стенд в публичный интернет и замените все секреты перед любым использованием за пределами локальной учебной сети.

## 1. Архитектура

- **Frontend:** React + TypeScript + Vite; Nginx отдаёт собранную SPA, проксирует API и перенаправляет HTTP на HTTPS.
- **Backend:** Python 3.11, Django 5.2, Django REST Framework, Gunicorn.
- **Database:** PostgreSQL 15; 8 доменных сущностей приложения: `User`, `ProjectRequest`, `Criterion`, `ExpertAssessment`, `PortfolioScenario`, `ScenarioRequest`, `CommitteeVote`, `AuditAndIntegrationLog`.
- **Внешние интеграции:** OpenLDAP для демонстрации входа и Mailpit как SMTP-ловушка для проверки писем.
- **Расчётное ядро:** `backend/ppm_app/services/` — независимые от Django ORM функции рейтинга, ранжирования, точного подбора портфеля, подсчёта голосов, проверки переходов статусов и CSV.

Все деньги обрабатываются через `Decimal`; алгоритм автоподбора работает с бюджетом в целых сотых долях, выбирает точный оптимум по ожидаемой выгоде, а при равенстве учитывает рейтинг, расход и ранги проектов. Журнал защищён от UPDATE/DELETE на уровне модели и триггером PostgreSQL.

## 2. Рекомендуемый запуск: весь стенд через Docker Compose

Этот вариант проще всего, если на VM уже работают Docker Engine и Compose: версия системного Python не важна, а PostgreSQL 15, OpenLDAP и Mailpit изолированы в контейнерах. Проверьте доступность командами `docker --version` и `docker compose version`. На дату подготовки проекта Debian 11 (Bullseye) уже не перечисляется в актуальном руководстве Docker как поддерживаемая версия для установки Engine; если Docker ещё не установлен, используй описанный ниже режим Arch + SSH-туннель к уже установленной PostgreSQL либо обнови VM до поддерживаемого релиза Debian. См. [официальную матрицу установки Docker для Debian](https://docs.docker.com/engine/install/debian/).

В корне проекта:

```bash
cp .env.example .env
python -c 'import secrets; print(secrets.token_urlsafe(48))'
```

Сгенерируйте ключ выше и вставьте его в `DJANGO_SECRET_KEY` в `.env`. Если открываете стенд с Arch-хоста через IP Debian VM, добавьте этот IP в `DJANGO_ALLOWED_HOSTS`, например:

```dotenv
DJANGO_ALLOWED_HOSTS=localhost,127.0.0.1,backend,192.168.122.50
```

Замените `192.168.122.50` на адрес своей VM. Затем запустите:

```bash
docker compose up -d --build
```

Первый запуск собирает контейнеры, создаёт схему БД, выполняет миграции и наполняет демо-данными. Проверка состояния:

```bash
docker compose ps
docker compose logs -f backend
curl -k https://localhost:8443/api/health/
```

Откройте:

- **Приложение:** `https://localhost:8443` (браузер предупредит о самоподписанном сертификате — это ожидаемо для учебного стенда).
- **Mailpit:** `http://127.0.0.1:8025` на самой VM. Для доступа с Arch-хоста откройте SSH-туннель `ssh -L 8025:127.0.0.1:8025 user@IP_ДЕБИАН_VM` и зайдите на `http://127.0.0.1:8025`.

Команды сопровождения:

```bash
docker compose logs -f backend
# остановить, сохранив БД
docker compose down
# остановить и удалить БД вместе с демонстрационными данными
docker compose down -v
```

## 3. Демо-учётные записи

| Роль | Логин | Пароль |
|---|---|---|
| Инициатор | `initiator` | `initiator123` |
| Эксперт 1 | `expert1` | `expert12345` |
| Эксперт 2 | `expert2` | `expert23456` |
| Менеджер портфеля | `manager` | `manager123` |
| Член комитета 1 | `committee1` | `committee123` |
| Член комитета 2 | `committee2` | `committee234` |
| Член комитета 3 | `committee3` | `committee345` |
| Администратор | `admin` | `admin12345` |

В Compose `LDAP_ENABLED=1`: учётные данные проверяются реальным bind к OpenLDAP. При пяти последовательных неудачных попытках вход блокируется на 15 минут. В локальном режиме из раздела 4 `LDAP_ENABLED=0`, и проверяется хеш пароля в таблице приложения.

## 4. Альтернативный запуск на Arch с уже установленным PostgreSQL в Debian VM

Этот режим переиспользует существующую PostgreSQL на Debian через SSH-туннель. Приложение и Vite при этом запускаются на Arch. Вход выполняется по локальным демо-паролям; LDAP и Mailpit будут отключены, если отдельно не настроить их адреса.

### На Debian VM — подготовить PostgreSQL

Подставьте свой пароль и выполните в `psql` от пользователя `postgres`:

```sql
CREATE USER ppm_user WITH PASSWORD 'ЗДЕСЬ_НАДЁЖНЫЙ_ПАРОЛЬ';
CREATE DATABASE ppm_db OWNER ppm_user;
```

Если роль/БД уже существуют, повторно их создавать не нужно. Проверьте локальное TCP-подключение к `127.0.0.1:5432` на самой VM; внешний порт PostgreSQL в интернет открывать не требуется.

### На Arch — создать туннель и окружения

В отдельном терминале:

```bash
ssh -N -L 5433:127.0.0.1:5432 user@IP_ДЕБИАН_VM
```

В другом терминале из каталога проекта:

```bash
cd backend
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

export DJANGO_SECRET_KEY="$(python -c 'import secrets; print(secrets.token_urlsafe(48))')"
export DJANGO_DEBUG=1
export DJANGO_ALLOWED_HOSTS=localhost,127.0.0.1
export DB_ENGINE=django.db.backends.postgresql
export DB_NAME=ppm_db
export DB_USER=ppm_user
export DB_PASSWORD='ЗДЕСЬ_ТОТ_ЖЕ_ПАРОЛЬ'
export DB_HOST=127.0.0.1
export DB_PORT=5433
export LDAP_ENABLED=0
export EMAIL_HOST=127.0.0.1
export EMAIL_PORT=1025

python manage.py makemigrations ppm_app
python manage.py migrate
python manage.py seed_demo
python manage.py runserver 127.0.0.1:8000
```

В третьем терминале:

```bash
cd frontend
npm install
npm run dev
```

Откройте `http://localhost:5173`. Vite проксирует `/api` на локальный Django. Для этого режима `npm` и Python-зависимости устанавливаются с репозиториев на твоём Arch; в текущем архиве не включены `node_modules` или виртуальное окружение.

## 5. Рекомендуемый сквозной демонстрационный сценарий

В seed-данных уже есть четыре заявки в статусе `UNDER_EVALUATION`, активный шаблон из четырёх критериев и готовые оценки двух экспертов.

1. Войдите как `manager`, откройте **Моделирование**, создайте сценарий с лимитом `30.00` млн руб. и нажмите **Автоматически подобрать**. Автоподбор должен уложиться в лимит.
2. При необходимости вручную включите/исключите проекты. При превышении бюджета передача комитету недоступна.
3. Нажмите **Передать комитету**.
4. По очереди войдите как `committee1`, `committee2`, `committee3` и проголосуйте за каждый включённый проект. Для фиксации требуется кворум не менее двух третей активных членов комитета по каждому проекту; доля «За» должна быть строго больше 50% от всех проголосовавших, включая «Воздержался».
5. Войдите как `manager`, откройте **Протоколы** и зафиксируйте решение. Затем экспортируйте утверждённые проекты кнопкой на вкладке **Заявки**.
6. Откройте `portfolio.csv`: он содержит BOM UTF-8, разделитель `;`, 10 столбцов `project_code`, `title`, `department`, `initiator_email`, `approved_budget_mln`, `effort_person_months`, `expected_benefits_mln`, `final_score`, `approval_date`, `protocol_id` и только проекты со статусом `APPROVED`. Идентификатор протокола в учебном MVP имеет вид `PPM-{id финализированного сценария}`.
7. Войдите как `admin` и проверьте журнал аудита. Для просмотра почтовых уведомлений используйте Mailpit.

Чтобы проверить полный цикл новой заявки: войдите как `initiator`, заполните форму и сохраните черновик либо нажмите «Создать и отправить»; затем как `manager` назначьте `expert1` и `expert2`; оба эксперта должны оценить каждый критерий своей учётной записью. После заполнения всех оценок система рассчитает интегральный рейтинг.

## 6. Тестирование

### Автоматические тесты расчётного ядра

Из `backend/`:

```bash
python -m unittest discover -s tests -v
```

Текущий набор содержит 24 теста, в том числе:

- тестовый пример `TC-FUNC-05`: рейтинг `3.75`;
- ранжирование и подбор `TC-FUNC-06`;
- сравнение точного подбора с независимым полным перебором на 300 воспроизводимых случайных наборах до 10 проектов;
- голосование и кворум `TC-FUNC-07`, обработка воздержавшихся;
- формат CSV `TC-FUNC-08`;
- границы валидации, переходы автомата статусов, запрет правки после начала оценки;
- проверку расчёта 100 проектов на соблюдение ограничения 5 секунд.

Результат прогонки в среде подготовки архива: **24/24 теста пройдены**. Это результат тестов чистых Python-функций, а не свидетельство прогона всего веб-стенда.

### Проверки полного стенда

После `docker compose up -d --build` проверьте:

- `GET /api/health/` возвращает `{"status":"ok","service":"ppm-api"}`;
- успешный вход и выдачу токена через `POST /api/auth/login/`;
- запрещённые роли получают HTTP 403;
- после 5 ошибочных паролей происходит блокировка учётной записи;
- письма доставляются в Mailpit или при отказе SMTP бизнес-операция сохраняется, а ошибка отражается в аудите;
- ручное превышение бюджета блокирует отправку сценария;
- без кворума итоговый протокол не фиксируется;
- `UPDATE`/`DELETE` строк аудита отклоняется триггером PostgreSQL.

Проверки браузеров, HTTPS, одновременной нагрузки в 50 пользователей и сквозные сценарии OpenLDAP/Mailpit следует прогнать отдельно на своём окружении. В отчёте ЛР6 не отмечай их как пройденные, пока не получишь реальные результаты со стенда.

## 7. Основные API-эндпоинты

| Метод и URL | Назначение | Роль |
|---|---|---|
| `POST /api/auth/login/` | Вход, выдача Bearer-токена | Все роли |
| `GET /api/auth/me/` | Текущий пользователь | Любая вошедшая роль |
| `GET/POST /api/requests/` | Реестр / создание черновика | Все роли с фильтрацией по роли; создание — инициатор |
| `PATCH /api/requests/{id}/` | Изменить свою заявку до оценки | Инициатор |
| `POST /api/requests/{id}/submit/` | Регистрация и выдача кода | Инициатор |
| `POST /api/requests/{id}/assign/` | Назначение экспертов и запуск оценки | Менеджер |
| `GET/POST /api/criteria/` | Просмотр/сохранение активного шаблона | Эксперт, менеджер, администратор; запись — менеджер/администратор |
| `GET/POST /api/assessments/` | Просмотр/сохранение экспертных оценок | Эксперт; сводный просмотр — менеджер/администратор |
| `GET/POST /api/scenarios/` | Реестр / создание сценариев | Менеджер; комитет видит переданные сценарии |
| `POST /api/scenarios/{id}/auto-select/` | Точный подбор портфеля | Менеджер |
| `POST /api/scenarios/{id}/toggle/` | Ручное включение/исключение проекта | Менеджер |
| `POST /api/scenarios/{id}/submit/` | Передача сценария комитету | Менеджер |
| `POST /api/committee/vote/` | Голос за проект в сценарии | Член комитета |
| `POST /api/committee/finalize/` | Проверка кворума и фиксация решений | Менеджер/администратор |
| `GET /api/protocols/` | Просмотр протоколов | Комитет, менеджер, администратор |
| `GET /api/export/portfolio.csv` | Выгрузка утверждённых проектов | Менеджер/администратор |
| `GET /api/admin/logs/` | Журнал с фильтрами | Администратор |

Все API-маршруты кроме health-check и login требуют заголовок `Authorization: Bearer <token>`.
